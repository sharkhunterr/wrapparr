# Wrapparr Constitution

## Core Principles

### I. Commits — Validation Explicite Obligatoire

Aucun commit ne DOIT etre execute sans validation explicite
prealable de l'utilisateur.

- Avant chaque `git commit`, le message exact et la liste
  complete des fichiers modifies DOIVENT etre presentes
- L'execution du commit DOIT attendre un "ok" ecrit
- Zero commit automatique, meme en fin de session, meme si
  le changement parait sans risque

**Raison** : l'utilisateur garde le controle total sur
l'historique Git du projet.

### II. Attribution — Aucune Mention IA

Aucune reference a "Claude", "Anthropic", "AI-generated",
"generated by" ou tout terme similaire ne DOIT apparaitre
dans les commits, commentaires de code, docstrings, README
ou tout autre fichier du projet.

- Les auteurs des commits sont uniquement ceux que
  l'utilisateur precise

**Raison** : propriete intellectuelle et presentation du
projet sans trace d'outil generatif.

### III. Langue — Convention Bilingue

- Code source (variables, fonctions, classes, commentaires
  techniques) : anglais
- Textes affiches a l'utilisateur final : francais
- Messages de commit : francais, convention Conventional
  Commits (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`)

**Raison** : coherence du codebase international avec une
UX francophone.

### IV. Securite

- Aucun secret hardcode — tout DOIT passer par les
  variables d'environnement
- Validation Pydantic v2 sur toutes les entrees API
- Cles API des services tiers chiffrees en base (AES-256)

**Raison** : conformite aux bonnes pratiques de securite
pour une application self-hosted exposee au reseau local.

### V. Validation Prealable — Avant de Coder

- Le plan ou le code DOIT etre montre avant ecriture sur
  disque
- La validation de l'utilisateur DOIT etre obtenue avant
  de passer a l'etape suivante
- En cas de doute sur une decision d'architecture, la
  question DOIT etre posee avant implementation

**Raison** : eviter le travail inutile et garantir
l'alignement continu avec la vision de l'utilisateur.

## Stack Technique Imposee

### Backend

- Python 3.12+ / FastAPI (async)
- SQLAlchemy 2.x async / Alembic / PostgreSQL 16
- Redis 7 (cache + sessions)
- APScheduler (jobs)
- python-jose (JWT) / httpx (async)
- Pydantic v2 pour tous les schemas

### Frontend

- React 18 + Vite
- Recharts / Zustand / React Router v6
- CSS-in-JS inline + CSS variables pour les themes
- Fonts : Google Fonts (Syne, Outfit, DM Mono)

### Infrastructure

- Docker + Docker Compose
  - `wrapparr-api` (FastAPI, port 8000 interne)
  - `wrapparr-frontend` (Nginx, port 80 interne)
  - `wrapparr-worker` (APScheduler)
  - `postgres`
  - `redis`
- Compatible Traefik (labels fournis)

### Variables d'Environnement Critiques

`DATABASE_URL`, `REDIS_URL`, `SECRET_KEY`, `ENCRYPTION_KEY`,
`TMDB_API_KEY` (optionnel), `FIRST_ADMIN_EMAIL`,
`FIRST_ADMIN_PASSWORD`

## Perimetre Fonctionnel & Architecture

Le prototype de reference est `wrapparr-front/src/slides/Wrapparr.jsx`.
C'est la reference visuelle absolue — aucune modification de
son apparence sans demande explicite de l'utilisateur.

### Modules fonctionnels

- **Authentification** : login local (bcrypt, JWT 15min +
  refresh httpOnly 7j), SSO OIDC configurable, roles
  admin/user/viewer
- **Collecteurs** : Plex (Tautulli), Jellyfin, ROMM,
  Audiobookshelf, Komga, Booklore
- **Generation recap** : pipeline collecte → normalisation →
  calcul stats → affiches (TMDB, OpenLibrary) → snapshot JSON
- **Slides** : intro, overview, cat-{service}, {service}-pod,
  {service}-main, {service}-deep, compare, ranking, finale
- **Podiums** : reveal 3 phases, phrases custom par
  utilisateur/categorie
- **Themes** : theme packs JSON, color picker, preview
  temps reel
- **Historique & replay** : snapshots immuables, /recap/{year}
- **Comparaisons** : N vs N-1/N-2/N-3, inter-utilisateurs
- **Partage** : lien public token opaque, expiration
  configurable
- **Admin** : dashboard, config globale, gestion theme packs,
  logs temps reel

## Governance

- Cette constitution est le document de reference supreme
  pour toutes les decisions de developpement sur Wrapparr
- Tout changement de principe DOIT etre documente, justifie
  et approuve par l'utilisateur avant application
- Les amendements suivent le versionnement semantique :
  - MAJOR : suppression ou redefinition incompatible d'un
    principe
  - MINOR : ajout de principe ou extension materielle
  - PATCH : clarifications, corrections de formulation
- Chaque revue de code DOIT verifier la conformite avec
  les principes ci-dessus
