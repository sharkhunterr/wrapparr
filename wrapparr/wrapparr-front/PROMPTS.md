```
Tu vas travailler sur Wrapparr — une application web self-hosted qui génère des récapitulatifs annuels visuels et animés (style Spotify Wrapped) pour un homelab. Elle agrège Plex, Jellyfin, ROMM, Audiobookshelf, Komga et Booklore.

Le dossier wrapparr-front/ contient le prototype React final validé (src/slides/Wrapparr.jsx). C'est la référence visuelle absolue — tu ne changes pas son apparence sans que je te le demande explicitement.

1. COMMITS

   - Tu n'écris jamais "Claude", "Anthropic", "AI-generated", "generated by" ou tout terme similaire dans les commits, commentaires de code, docstrings, README, ou n'importe quel fichier du projet

   - Code source : anglais (variables, fonctions, classes, commentaires techniques)
   - Textes affichés à l'utilisateur : français
   - Messages de commit : français, convention Conventional Commits (feat:, fix:, refactor:, docs:, chore:)

4. SÉCURITÉ
   - Aucun secret hardcodé — tout passe par les variables d'environnement
   - Validation Pydantic v2 sur toutes les entrées API

5. AVANT DE CODER
   - Tu me montres toujours le plan ou le code avant de l'écrire sur disque
   - Tu attends ma validation avant de passer à l'étape suivante
   - Si tu as un doute sur une décision d'architecture, tu me poses la question avant d'implémenter

---

STACK TECHNIQUE IMPOSÉE :

Backend :
- Python 3.12+ / FastAPI (async) / SQLAlchemy 2.x async / Alembic / PostgreSQL 16
- Redis 7 (cache + sessions) / APScheduler (jobs) / python-jose (JWT) / httpx (async)
- Pydantic v2 pour tous les schémas

Frontend :
- React 18 + Vite / Recharts / Zustand / React Router v6
- CSS-in-JS inline (cohérent avec le prototype) + CSS variables pour les thèmes
- Fonts : Google Fonts (Syne, Outfit, DM Mono) — déjà dans le prototype

Infra :
- Docker + Docker Compose
- Nginx pour servir le frontend build
- Compatible Traefik (labels fournis)

---

PÉRIMÈTRE FONCTIONNEL (ce que Wrapparr doit faire) :

Authentification :
- Login local (email + mot de passe, bcrypt, JWT 15min + refresh token httpOnly 7j)
- SSO OIDC configurable : Authentik, Keycloak, Authelia, ou tout provider OIDC standard
- Rôles : admin (tout), user (son propre recap), viewer (lecture seule via lien partagé)

Collecteurs de données :
- Plex via Tautulli (films, séries, durées, habitudes temporelles, genres)
- Jellyfin (API native, mêmes métriques)
- ROMM (jeux, heures, plateformes, genres, décennies, sessions)
- Audiobookshelf (livres audio, heures, habitudes d'écoute)
- Komga (volumes, séries, genres, jours de lecture)
- Booklore (livres, auteurs, genres)

Génération du recap :
- Pipeline : collecte → normalisation → calcul stats → récupération affiches (TMDB, OpenLibrary) → snapshot JSON
- Planification configurable (défaut : 1er janvier 2h00)
- Déclenchement manuel depuis l'admin ou le profil
- Progression en temps réel (WebSocket ou polling)

Slides & présentation :
- Types : intro, overview, cat-{service} (annonce), {service}-pod (podium), {service}-main (stats), {service}-deep (habitudes), compare, ranking, finale
- Activation/désactivation par slide et par utilisateur
- Ordre configurable (drag-and-drop) sauf intro (toujours 1er) et finale (toujours dernier)
- Skip automatique si service non connecté ou données insuffisantes
- Ordre validé dans le prototype : annonce catégorie → podium → stats principales → stats détaillées

Podiums :
- Reveal en 3 phases : attente (pulse rings) → phrases rigolotes → reveal #3/#2/#1
- Phrases par défaut par catégorie avec variables ({user}, {count}, {hours}, {year}, {top1})
- Phrases custom par utilisateur/catégorie (ajout, suppression, réordonnancement)
- Mode "mélange" ou "remplacement" des phrases custom vs défaut

Thèmes visuels :
- Theme packs : objet JSON complet (palette, card_style, transition, particles, orbs, grain, spotlights, finale_effect, fonts)
- Packs livrés : cinematic (défaut, celui du prototype), neon-arcade, editorial, galaxy, ember
- Personnalisation : color picker sur les couleurs principales, toggle sur chaque effet
- Prévisualisation temps réel
- Scope : thème global (admin) + thème personnel (si allow_user_themes = true)

Historique & replay :
- Chaque recap généré est sauvegardé comme HistorySnapshot immuable
- Replay avec le thème et la config de l'époque
- Page /recap/{year} pour accéder à un recap passé

Comparaisons :
- N vs N-1, N-2, N-3 sur toutes les métriques principales
- Graphiques superposés activité mensuelle
- Comparaison inter-utilisateurs si allow_user_comparison = true (masquable par user)

Partage :
- Lien public avec token opaque, expiration configurable
- Accès sans auth, données personnelles minimales, classement inter-users masqué

Admin :
- Dashboard : users, services, jobs, logs temps réel
- Config globale : allow_registration, allow_user_themes, allow_user_comparison, recap_schedule, SMTP, max_history_years, public_share_expiry_days
- Gestion des theme packs (CRUD, upload JSON custom)

---

ARCHITECTURE DES SERVICES DOCKER :
- wrapparr-api (FastAPI, port 8000 interne)
- wrapparr-frontend (Nginx, port 80 interne)
- wrapparr-worker (APScheduler)
- postgres
- redis

VARIABLES D'ENVIRONNEMENT CRITIQUES :
DATABASE_URL, REDIS_URL, SECRET_KEY, ENCRYPTION_KEY, TMDB_API_KEY (optionnel), FIRST_ADMIN_EMAIL, FIRST_ADMIN_PASSWORD

3. Une question ou ambiguïté que tu vois déjà dans les specs

N'écris aucun code. Attends mes instructions.
```

## PROMPT 2 — SPECIFY (plan d'implémentation)

> À coller après avoir validé la réponse au Prompt 1.

---

```
Bien. Maintenant je veux le plan d'implémentation complet avant qu'on commence à coder.

Le dossier de référence est wrapparr-front/ — c'est le prototype React validé (src/slides/Wrapparr.jsx) qu'on va intégrer dans l'app complète.

Donne-moi le plan structuré en phases, dans cet ordre de priorité :

PHASE 1 — Squelette Docker fonctionnel
- docker-compose.yml avec les 5 services (api, frontend, worker, postgres, redis)
- Dockerfile backend + Dockerfile frontend
- .env.example complet
- Vérification : docker compose up → tous les services démarrent

PHASE 2 — Backend Auth (Module le plus critique)
- Modèles SQLAlchemy : User, RefreshToken, OIDCProvider
- Schémas Pydantic v2 correspondants
- Helpers sécurité : bcrypt, JWT access/refresh, AES pour les clés API
- Endpoints : POST /api/v1/auth/login, /logout, /refresh
- Endpoints SSO OIDC : /auth/sso/{provider}/authorize + /callback
- Migrations Alembic (auto-appliquées au démarrage)
- Tests unitaires auth

PHASE 3 — Connecteurs & collecte de données
- Base class collecteur (interface commune)
- Collecteur Tautulli/Plex
- Collecteur ROMM
- Collecteur Audiobookshelf
- Collecteur Komga
- Collecteur Jellyfin
- Collecteur Booklore
- Endpoint test de connexion pour chaque collecteur
- Job APScheduler pour la collecte annuelle

PHASE 4 — Génération du recap
- Modèles SQLAlchemy : ServiceConnector, YearlyRecap, HistorySnapshot
- Pipeline de génération (collecte → normalisation → calcul → TMDB → snapshot)
- Proxy TMDB + OpenLibrary côté backend
- Endpoints recap : GET /api/v1/recaps, GET /api/v1/recaps/{year}, POST generate, GET compare

PHASE 5 — Frontend connecté à l'API
- Intégration du prototype wrapparr-front/src/slides/Wrapparr.jsx dans l'app
- Store Zustand : données recap, user, thème
- Hook useRecap : fetch depuis l'API
- Remplacement des données mock (const D = {...}) par les données API
- Page login (local + boutons SSO)
- Guard de route (redirect si non auth)

PHASE 6 — Configuration slides & thèmes
- Modèles : SlideConfig, ThemePack, CustomPhrase
- CRUD API pour chaque
- UI préférences user : activation slides, ordre drag-and-drop, phrases custom
- UI sélection thème + color picker + preview iframe
- ThemeProvider React : charge le thème actif, injecte les CSS variables

PHASE 7 — Admin
- Dashboard avec métriques
- Gestion users (liste, création, désactivation, reset password)
- Config globale (formulaire)
- Gestion theme packs (CRUD)
- Logs temps réel (WebSocket)

PHASE 8 — Historique & partage
- Page /recap/{year} avec replay exact (thème + slides de l'époque)
- Slide compare multi-années
- Génération token partage public
- Route /share/{token} sans auth

---

Pour chaque phase :
- Liste les fichiers à créer
- Identifie les dépendances avec les autres phases
- Note la complexité (Simple / Moyen / Complexe)
- Signale les décisions techniques que je dois valider avant de coder

À la fin, propose-moi par quelle phase commencer et montre-moi le premier fichier qu'on va créer ensemble.

Aucun code écrit sur disque avant ma validation. Aucun commit sans mon "ok".
```
